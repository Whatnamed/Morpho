**整体判断：Morpho 的架构方向是合理的，已经具备真实的单 Agent 工具循环和较完整的执行可靠性基础；但还不能把它视为可靠的长程设计任务 Harness。当前最需要补的是 Context 连续性、任务收尾判定、按需取证和生成后的视觉反馈，而不是增加更多 Agent 角色。**
审计基于当前 `D:\Morpho` 工作区，包含既有未提交改动，HEAD 为 `8c17c9f`。我核对了产品合同、实际调用链和测试，并做了离线运行时复现。本轮没有修改代码或文档，也没有调用付费模型。
目前的实际链路是：

```
用户输入与选择
→ Strategy / Method Packs / Context / Memory 组装
→ 单 Agent Responses 请求
→ 本地校验与工具执行
→ 工具结果进入下一次模型请求
→ 最终回答、确认卡或中断

Coordinator + Lifecycle + Journal + Recovery 负责执行状态与恢复
```

这确实构成了 Agent loop。问题主要出在：**执行链能继续，不等于设计任务能持续取得进展；请求正常结束，也不等于本轮目标已经满足。**
以下是我认为真正影响架构判断的发现。
**1. Context 连续性存在已复现的断点，应当最先修复。**
产品合同要求“预算内完整携带未压缩历史”，实际请求组装却先取最近 24 个 Context frames，再将 frames、历史和当前输入整体截为最近 96 项。
我用当前 Runner 和仓库现有 Fake Host 做了离线复现：放入 110 条很短的历史消息后，实际请求只有 **95 条历史消息＋当前输入，Project State 和 Turn Context frames 都被截掉**。原始消息仍在本地，损失发生在模型实际收到的输入中。
这意味着长期项目里，模型可能仍能聊天，却已经失去当前项目状态、稳定记忆投影和本轮范围说明。[请求组装代码 (line 379)]\(D:/Morpho/src/features/workspace/agentTurnProductPreparationAPlus.ts:379)
自动压缩还有第二个断点：Runner 先准备请求，再执行压缩；压缩成功后，没有重建即将发送的请求。续轮也继续复制原来的 `providerBaseRequest`。
离线复现结果是：**摘要成功持久化，但紧接着发出的请求没有新摘要，仍携带已覆盖的原始内容。** 压缩可能惠及后续用户回合，却未正确服务当前执行链。[首次请求路径 (line 161)]\(D:/Morpho/src/features/workspace/agentTurnRunner.ts:161)、[续轮请求路径 (line 1363)]\(D:/Morpho/src/features/workspace/agentTurnRunner.ts:1363)
此外，完整 Provider timeline 的预算与 frame 筛选辅助机制虽然存在，但没有接入正式调用链；部分债务也已在仓库文档中明确记录。[已记录的架构债务 (line 81)]\(D:/Morpho/docs/architecture/ai-capability-layer.md:81)
**建议：先让“实际发送的输入”成为唯一预算对象，覆盖 System、工具 Schema、frames、历史、图片和工具结果；压缩后重建下一请求，同时保留已经发送请求的原样重试身份。** 这比更换 Memory 方案或扩大上下文窗口重要得多。
**2. 当前缺少可靠的收尾检查，部分“机制存在”仍停留在辅助函数或提示层。**
历史、记忆和进度问题有 required-read resolver、读取范围校验和提醒状态，但检查最终回答前是否完成必需读取的函数，没有接入正式 Runner 的收尾路径。
我模拟用户询问“最早的对话是什么？”，模型直接回答“没有记录。”而不调用工具。实际结果是：**只发生一次 Provider 请求，回答被标记为** **`success`****\*\*\*\*。**
Memory 的所谓“确定性补检”目前也是预先加入请求的一条提醒。模型可以忽略它直接结束；现有测试明确接受这种情况。[读取检查函数 (line 106)]\(D:/Morpho/src/features/workspace/agentTaskStrategy.ts:106)、[Memory 提醒实现 (line 409)]\(D:/Morpho/src/features/workspace/agentTurnProductPreparationAPlus.ts:409)、[对应测试 (line 338)]\(D:/Morpho/src/features/workspace/agentTurnRunner.test.ts:338)
这里还有一个结构性限制：服务端只要看到响应没有工具调用，就将整个 Server Turn 结算为 `externallyCompleted`。因此，客户端发现遗漏后，不能直接沿原协议补一轮检查。[服务端结算 (line 271)]\(D:/Morpho/src/app/api/ai/agent/turns/[turnId]/requests/handler.ts:271)
**建议：区分 Provider 请求结束、外部执行结束、本地任务验收三个概念。** 不必让服务端判断设计质量，但 Harness 应能在最终接受回答前检查：

- 要求读取的来源是否真的读过；
- 声称创建的成果是否实际存在；
- 明确需要处理的记忆候选是否已处理或明确跳过；
- 是否还有失败项、待确认事项或未满足的要求。

这不是新增一个 Critic Agent，而是把已有合同接到真正的完成边界上。
**3. 按需读取能力偏窄，限制了 Research 和设计探索的自主推进。**
现有读取工具主要是选择范围、项目记忆、阶段记录和聊天搜索。其中 `read_selected_context` 没有对象参数，返回的是准备阶段已经构建好的 Context，不能根据刚发现的 object ID 继续深入读取。
文档默认只取每份前 8,000 字符、总计 24,000 字符；虽然会标注截断，但没有对应的分页、定位或补读工具。模型知道资料没读完，也无法自己继续读。[读取工具注册 (line 163)]\(D:/Morpho/src/features/workspace/agentToolExecutors.ts:163)、[选择范围读取 (line 193)]\(D:/Morpho/src/features/workspace/agentToolExecutors.ts:193)、[文档摘录 (line 23)]\(D:/Morpho/src/features/workspace/documentContext.ts:23)
Research 已有真实外部搜索、引用归集、失败统计和研究对象落地，这是可用基础。不过当前正式搜索路径主要是 DuckDuckGo 搜索结果加 Jina 摘录，网页正文最多取前 18 个非空行、1,200 字符，也没有独立的后续页面读取能力。[搜索实现 (line 31)]\(D:/Morpho/src/server/ai/webSearch.ts:31)、[页面摘录 (line 168)]\(D:/Morpho/src/server/ai/webSearch.ts:168)
因此它适合发现案例、补充线索；对需要核对产品机制、使用条件、来源冲突的研究任务，证据获取深度不足。**有引用，只能证明找到来源，不能证明来源充分支持结论。**
合理的补充是少量领域读取能力：查找项目对象、按 ID/修订读取、读取文档指定片段、查看指定图片、展开已发现网页。保留现有隐藏对象和授权边界即可，暂时没有证据说明必须引入向量数据库、通用浏览器 Agent 或复杂 RAG 平台。
**4. 图像生成前的约束较完整，生成后的判断闭环明显不足。**
现有图像链路值得保留：

- Agent 输出结构化视觉意图；
- 引用解析和 `ImagePromptCompiler` 组合保留项、修改项与设计背景；
- 批次检查用户要求的数量；
- 每张图独立提交，失败和取消保留已完成结果；
- 新图不覆盖来源图。

但 `generate_visuals` 返回给模型的主要是对象 ID 和失败项，**不会将新生成的像素加入当前续轮输入，也没有工具让 Agent 随后读取这些像素**。[生成工具返回值 (line 579)]\(D:/Morpho/src/features/workspace/agentToolExecutors.ts:579)
所以目前可靠成立的是：

> 用户看结果 → 选中图片 → 再次提问或继续发展。

尚未成立的是：

> Agent 生成 → 观察真实结果 → 对照要求判断 → 有依据地修正或说明不足。

这对工业设计尤其关键。“保留结构、只改 CMF”写进生成请求，不代表生成结果真的保留了结构。
**建议优先补充有条件的生成后观察**：当用户要求比较、检查、一致性保持或选优时，让 Agent 读取结果图，对照来源和约束说明具体差异。普通出图不必强制增加一次模型调用；发现偏差也不应默认无限重生成或自动替用户选方向。
**5. 长任务需要轻量任务状态和进展判定，尚不需要独立 Planner。**
当前 Strategy 回答的是“本轮属于哪类工作”，Visual Plan 回答的是“本批要生成哪些图”；Journal 和 Recovery 回答的是“哪个请求执行到了哪里”。这些都不是完整的任务分解。
对于“补充案例→提炼差异→提出三个方向→检查覆盖情况”，尚缺少一个紧凑、可恢复的任务记录，连接目标、已完成成果、剩余证据缺口和停止原因。
运行时已有步数、服务端计数和截止限制，但语义上的无进展检测没有完整接线。离线复现中，模型使用不同 call ID 连续五次调用相同的 `read_selected_context`，五次都执行，最后仍正常成功。请求幂等保护解决不了这种重复工作。
**值得增加的是任务级工作记录，而不是默认先调用一个 Planner 模型：**

- 当前目标和范围；
- 本轮成功条件；
- 已取得的成果与来源 ID；
- 剩余问题、等待用户决定的事项；
- 成本预算和停止原因。

简单讨论可以完全不创建这种记录。复杂任务可以由同一个 Agent 按需提出短计划，运行时负责记录和核对；这些内部信息也不需要变成用户可见的任务管理中心。
刷新恢复方面，现有 exact request、执行意图预写、Journal 查询和局部成果保存已经有价值。应继续保持“执行恢复”和“项目跨回合连续性”的区别，不必把它改造成离开页面后持续自治的后台系统。
**6. Eval 的主要缺口是整链行为证据，而不是再增加一份方法清单。**
当前 Eval corpus 覆盖的设计场景合理，包含方向发散、成熟草图延续、CMF 保留边界、具体批评和历史追问。但其主要形式是定性验收描述与确定性单元覆盖，尚不能证明实际模型在完整 Harness 中稳定完成这些任务。[Eval corpus (line 1)]\(D:/Morpho/docs/architecture/ai-capability-eval-corpus.md:1)
本轮 **16 个测试文件、241 项测试全部通过**，同时上述 Context 丢失和必需读取遗漏仍可复现。这说明测试已经较擅长证明局部模块正确，接下来需要加强“真实 Runner 最终给模型什么、最终接受什么”的验证。
建议沿用现有 Fake Host 和 Coordinator 测试设施，补充少量完整轨迹验收：

- 长历史中约束与当前状态不丢失；
- 压缩之后下一请求确实切换到新摘要；
- 忽略必需读取不能直接通过验收；
- 工具失败、恢复和重试不重复产生结果；
- 生成后的评价确实依据结果像素；
- 发散方案在设计变量上有差异，收敛建议有明确依据。

专业质量再通过固定场景的真实模型抽样和人工评审判断，关注任务完成、约束遵守、证据支撑、成本与延迟。**不要把工具调用次数、反思次数或回答长度当成 Agent 能力指标。**
有几部分，我明确建议保留。
首先，**一个项目、一个连续 Agent、一个权威项目状态**适合 Morpho。Strategy 和 Method Packs 按任务组合也合理，没必要按研究、设计定义、视觉发展拆成彼此独立的聊天或角色。
其次，**来源驱动 Memory Kernel、当前投影、修订历史和** **`reviewRequired`** 比自由生成的“Agent 长期记忆”更符合设计协作。主要问题在输入接线和读取覆盖，不在于缺少更复杂的记忆存储。
再次，**Proposal、确认边界、不可覆盖的图像对象、方向修订与来源关系**，已经给发散、收敛和回头继续旧路线提供了不错的数据基础。应让 Agent 更好地读取和解释这些关系，不需要额外建立全项目回滚或搜索树。产品规则本来也明确采用“从旧图继续新路线”的方式。[版本与旧图继续规则 (line 206)]\(D:/Morpho/docs/product/04_Morpho_状态、版本、项目记录与记忆.md:206)
最后，**本地工具权限、严格参数校验、执行恢复、部分成功保存**是现有 Harness 的强项。这里的判断限于本地代码和测试证据，不代表已经验证线上服务和所有故障场景。
对于常见 Agent 机制，我的取舍如下：

| 机制对 Morpho 的判断   |                                  |
| ---------------- | -------------------------------- |
| 独立 Planner Agent | 暂不引入；先补复杂任务的轻量工作记录               |
| Critic           | 值得按需引入“检查步骤”；先不拆成常驻角色            |
| Reflection       | 做有依据、有上限的检查与修正；不默认每轮追加自我反思       |
| Multi-Agent      | 当前不值得作为主架构；未来仅在可独立并行的研究子题上评估     |
| 自动迭代生成           | 只在用户目标、成本范围和可判断标准明确时使用           |
| 通用 Agent 框架      | 没有必要；现有 Coordinator、工具和领域层足以承接演进 |

发散阶段应检查方向是否覆盖不同设计变量，避免过早用统一评分消灭探索；收敛阶段才加强约束、取舍和证据检查。一个笼统的“设计质量 Critic”容易把这两种任务混在一起。只有评价标准明确、迭代收益可测时才引入 evaluator–optimizer，也符合官方架构建议。[Anthropic：Building Effective Agents](https://www.anthropic.com/engineering/building-effective-agents)
**合理的演进顺序是：先修连续性和完成边界，再补领域读取与视觉反馈，最后根据 Eval 决定是否增加规划或独立评审。** 第一阶段就应以实际请求和故障轨迹为验收依据；不要一边保留这些断点，一边叠加 Planner、Critic 和 Multi-Agent。
