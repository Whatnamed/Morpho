# Morpho 下一阶段产品与工程方向（过渡说明）

更新日期：2026-11-19

状态：下一代产品方向讨论中，尚未形成正式产品规格或实施计划。

## 1. 文档定位

Morpho 将进入一次较大的产品、Agent 与工程体系调整。本文整理目前已经明确的目标、方向性偏好和尚未决定的事项，供后续产品讨论、技术选型、遗留清理及 Coding Agent 理解项目使用。

- 现有 v3.2 产品文档与当前代码仍是现行产品行为和实现的依据。本文用于判断下一阶段的适用性，不将尚未定稿的想法当成已经实现或批准实施的需求。
- 现有规范中涉及单一连续会话、固定聊天区域、阶段与记忆组织、Context 策略、Agent Runtime、视觉设计系统等内容，允许在新阶段重新评估；不得仅因旧文档将其列为约束，就认为未来必须保留。
- 现阶段允许提出大范围重构、替换、合并、删减和架构迁移建议。具体产品与关键架构决策由项目负责人确认，实际修改以相应任务授权为准。

待新版产品方案确定后，将已确认规则统一写入正式产品、设计和架构文档，本文不再作为独立长期规范维护。

## 2. 核心目标与工作重心

Morpho 仍面向产品与工业设计，目标是让 AI 真正参与设计研究、问题定义、概念探索、视觉表达、深化和迭代等工作，并与设计师的实际工作过程相结合。

下一代 Morpho 以**桌面端 Design Agent** 为主要发展方向。是否继续提供浏览器 Web 版本尚未决定。桌面端的应用框架、进程组织、存储和分发技术留待选型。

下一阶段优先提升三个方面：

- **专业设计能力**：让 Agent 在真实设计任务中提供有实质价值的分析、方案和迭代支持，而非仅生成文字或图片。
- **核心设计流程与使用体验**：改善设计师和 AI、画布、项目资料之间的连续交互，提高工作的灵活性与效率。
- **研发与迭代效率**：让 Agent 的组成、行为与能力能够方便调整、替换、观察和测试，并降低代码及文档的理解和维护成本。

完整产品的外围功能、品牌完善、独立调研产品、分发及其他扩展需求仍有价值，但暂不优先于上述核心目标。

## 3. Design Agent、Harness 与专业能力

### 3.1 Agent 研发方向

希望将 Morpho 进一步发展为面向设计任务的 Agent/Harness 产品。其与画布、项目资料和实际设计流程应形成有机整体，而非简单的设计特化聊天工具。

Agent Loop、Harness、Prompt、Skill、Tool、Context、Memory、Session 等应根据实际任务需求重新审视。具体机制及其职责边界尚未确定，不预先选择某种 Loop、Multi-Agent 模式、Skill 系统、Tool 粒度或固定编排方式。

项目负责人希望先了解成熟 Agent 的机制及真实实现，再亲自主导专业设计策略、System Prompt、Skill 内容、Tool 定义与组合、Loop 和 Context 行为的设计及反复测试。Coding Agent 可以提前建设工程基础、实现已明确的能力、提供简单的初始方法和调试样例，但不应自行将大量时间投入专业设计策略的最终设计或优化。

### 3.2 复用与现有工程基础

优先利用成熟开源项目、组件及现有 Morpho 的有效实现。Pi、OpenCode、OpenHands、OpenDesign 等是值得参考的实现，不是必须采用的技术路线。需要时也可以借鉴其他领域成熟 Agent 的组织方式。

当前 A+ Runtime 是运行基线，而非下一代架构的永久约束。可根据新目标及实际证据对其进行简化、局部替换或整体重构；避免保留一套完整旧编排后再叠加另一套 Loop。

已交付的 Agent Lab 提供本地配置、独立运行、实际 Provider 输入观察以及工具调用与续传记录。应优先利用这些基础进行后续调试；其实现同样可以随实际架构变化调整，不要求继续扩建独立实验平台。

### 3.3 专业知识、工具与评估

考虑引入产品及工业设计专业知识、方法、案例、材料与工艺资料、人机工程数据等，并结合资料读取、检索、计算和其他实际工具提高 Agent 能力。RAG、知识库、结构化数据库、外部 Tool 或 Skill 都是待评估的实现方式，尚未确定采用哪一种或如何组合。

设计能力的实际评判由项目负责人主导。可利用代表性案例比较不同模型、Prompt、Tool、Skill、Loop 与 Context 配置的结果；客观事实、资料送达、执行正确性、权限、成本等可采用适当自动检查。暂不建设大型 Eval 平台，也不默认由另一个 LLM 决定专业设计结果的优劣。

## 4. 产品形态、工作台与会话

### 4.1 Canvas 与 Agent

当前倾向继续保留无限画布与工作台，将其与 Agent 深度融合，而非直接改成以聊天列表为主的通用 Agent 产品。AI 交互在未来工作过程中占比会很高，不能再被过于固定的侧边栏限制。

目前偏好的交互方向：画布作为基础工作空间，聊天界面可以作为其上的灵活界面，支持移动、缩放、吸附、最小化以及半屏、全屏等使用状态。初始位置和默认形态可以参考现有工作台。是否另提供独立的聊天主导模式、两种布局自由切换等，待 UI/UX 方案确定。

这些是产品形态的方向性偏好，不是已经定稿的面板规格或布局架构。是否以及如何继续使用 tldraw，需要结合实际画布能力、集成方式和未来分发许可判断；尚未决定更换 Canvas SDK。

### 4.2 项目内多会话与记忆

下一代产品希望支持一个项目内创建和管理多个 AI 会话，而不是强制所有设计讨论集中于一个永远延续的线程。

不同会话服务于同一项目，项目资料及有效项目记忆应能够为相关会话所用；具体的 Session 边界、历史组织、上下文压缩、会话与项目记忆的关系、信息共享范围以及记忆更新规则仍需设计。现有七类项目记忆、阶段记录及固定 Context 策略均可重新评估。

跨项目、跨会话的全局或个人长期记忆属于进一步探索方向，不等同于本次项目内多会话需求，暂不优先实施。

### 4.3 UI/UX 与资料管理

准备重新设计整体 UI/UX、交互和 Design System。旧视觉、组件及交互规则用于维持现行产品，不应限制新版设计探索。新版仍需服务真实设计流程，而非单纯视觉风格更新。

项目资料的管理与表现形式也计划重新考虑，具体结构、操作和呈现尚待补充需求。可提前完善明确有用的通用文档、图像和多模态读取能力，以及 Workspace/Canvas 的底层操作能力；不要据此提前决定正式产品的 Tool 体系、资料组织方式或数据架构。

品牌、Logo、独立图标设计及现有 Lucide 图标的取舍暂未确定，可在主要产品体验形成后安排。此前 Miora 的品牌探索可作为参考。

## 5. 工程演进与维护原则

当前浏览器运行时、浏览器存储、跨标签页和断线恢复机制、服务端架构及部署方式均属于现行 Web 实现。桌面端可根据实际的数据、执行和交付需求重新选择。

下一阶段会结合多种 Coding Agent 进行开发，不应依赖某一模型对历史长上下文或隐含规则的特殊理解能力。

- 以当前实现、实际调用关系、真实需求及 Git 历史判断现有机制的价值。区分仍有用的保护、过度复杂的实现、已废弃功能遗留以及等待新产品决策的机制。
- 允许大规模重构、替换和删除不适合新目标的代码、依赖、测试及文档；过去的开发投入或验收不构成永久保留理由。优先选择清晰直接的结构，而非为了兼容旧设计增加层次。
- 降低理解和修改成本：明确命名、职责、状态所有权与模块边界，减少重复实现、无效防御、过度抽象及缺乏实际消费者的机制。保留仍然有效的数据完整性、权限、安全及防止重复外部付费等必要保护，允许以更简单的实现满足这些需求。
- 正式文档应简洁、准确、易于定位，区分当前事实、确认决策与历史材料。避免把所有历史变更、验收过程、重复规则和防御性声明堆入日常开发入口。
- 优先通过现有库、标准接口和成熟开源实现解决问题，不因追求未来通用性而预建复杂框架、兼容层或工具平台。

遗留清理与架构适用性审查应同时考虑现行产品和下一阶段方向。已明确无用或不合理的设计可以列为近期改造建议；依赖尚未确定的新产品、数据或 Agent 架构的部分应明确等待决策，不必现在精修未来可能整体替换的模块。审查任务本身不意味着获得修改权限。

## 6. 暂缓或独立探索的方向

- **产品调研系统**：希望支持从不同起点出发的灵活调研，尤其是实际产品、竞品、设计作品、图文及外形、材质、结构比较；可考虑接入电商、社交、设计社区及其他真实资料来源。独立产品、Morpho 内置功能或可集成的混合形式仍开放，已分流讨论，暂不进入 Morpho 主线实施。
- **分发与部署**：考虑开源、可下载本地运行的 Agent/Harness 产品，以及未来域名、服务器和中国大陆可访问的演示环境。桌面应用的分发渠道、许可、演示部署和云存储仍待决定，当前偏好 local-first。
- **外围扩展**：跨项目全局记忆、品牌细化、额外产品形态等不作为当前核心开发的前置条件。此前关于 ChatGPT MCP/tldraw 插件的讨论不属于 Morpho 项目需求。
