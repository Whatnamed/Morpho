## 1. Morpho 是什么

### 1.1 一句话定义

**Morpho 是面向产品设计 / 工业设计概念阶段的 AI 辅助设计工作台。**

它把前期输入与调研、方向探索、设计定义、连续视觉发展与交付准备放进同一个连续项目空间里，让用户不必在聊天工具、生图平台、Figma、文件夹和临时笔记之间反复搬运信息。

### 1.2 它解决的不是“少一个生图工具”

概念设计阶段的实际断裂通常发生在这里：

```text
用户有一批参考、草图、课程文件和模糊想法
→ 到处聊天、搜索、截图、生成
→ 结果图越来越多，但为什么选它、从哪来、改过什么逐渐丢失
→ 交付时重新找图、补理由、补结构、补叙事
```

Morpho 的目标不是替代每一个专业软件，而是把这段最容易断裂的概念过程留在一个项目里：

```text
输入资料与起点
→ 理解、分析与调研
→ 设计定义
→ 方向与视觉发展
→ 按需设定后续默认参考
→ 交付准备与导出
```

用户看到的是一张连续画布和一个连续 Agent 会话；系统在后台保持结构化项目事实、当前有效项目记忆、阶段记录、压缩摘要和对象关系，使 AI 能在不反复“重新认识项目”的前提下继续工作。

### 1.3 当前产品边界

Morpho 当前服务的是：

```text
产品 / 工业设计的概念阶段
+ 视觉概念与外观语言探索
+ 调研、判断、设计定义和方向收束
+ AI 图像生成、编辑与表达素材扩展
+ 展板、PPT、作品集等交付材料的整理
```

Morpho 当前不把自己定义为：

```text
CAD 建模工具
工程结构、受力、制造、DFM 或量产验证工具
严格尺寸、BOM、供应链或生产管理工具
项目管理、任务看板或企业协同平台
自动替用户完成真实网页调研的黑箱代理
替代 Figma、Keynote、Illustrator 等专业精修 / 排版工具
```

它可以帮助用户在交付前整理内容、搭建可编辑的交付结构和发现表达缺口，但不承诺在第一阶段一键产出完全不需人工检查的最终展板、PPT 或商业文件。

## 2. 核心用户与使用场景

### 2.1 第一阶段核心用户

第一阶段优先服务：

- 产品设计、工业设计学生；
- 还在形成方法的初学者；
- 需要快速完成概念方案和展示材料的早期 ID 设计师；
- 独立设计师、个人创作者；
- 有实际项目，但前期资料、图像与表达材料容易散掉的人。

这些用户通常不缺工具入口，而是缺一条稳定的工作路径：他们可以生成图，但不容易把“资料—判断—方向—主图—交付”连起来，也难以在设计反复调整后保持可追溯性。

### 2.2 典型起点

Morpho 不要求用户从一个标准 Brief 表单开始。常见进入方式包括：

```text
一句模糊想法
一份课程题目或比赛 Brief
一批参考图、竞品截图或网页链接
手绘草图、旧渲染、已有模型截图
一份 PDF、PPT、Word 或调研资料
一个已经成熟、只需做主图和交付的方案
```

因此，新建项目后不强制填写名称、类别、交付物或固定项目表单。用户可以先写一句话、粘贴图片、拖入资料，或直接在右侧说“我还不知道从哪里开始”。

### 2.3 核心场景

| 场景 | 用户真实需求 | Morpho 的作用 |
|---|---|---|
| 从模糊主题开始 | 先找到可研究、可设计的切入点，而不是立刻硬生图 | 用探索与调研形成可继续的方向线索 |
| 带着一堆资料开始 | 先理解资料之间的关系，不愿逐张建文件夹 | 直接放进画布，在当前任务里选择并讨论 |
| 从研究走向设计 | 不想让调研停在摘要或关键词 | 把可保留的结论收束为设计定义与方向依据 |
| 生成多个方向 | 不希望只靠文字选一个方案 | 让方向尽早有可视预览，再讨论差异与取舍 |
| 持续迭代主图 | 希望保住已经成立的架构与视觉基线 | 以主图、版本和锚点维持可追溯的连续发展 |
| 补齐表达素材 | 不知道该补哪些图，也不想机械凑“标准图种” | 从当前交付目标和已有内容判断缺口 |
| 整理展板 / PPT | 交付前总在重新找图、补文字、补逻辑 | 复用项目内已有对象，建立可编辑交付结构 |

## 3. Morpho 的核心价值

### 3.1 从工具切换变成一个连续项目

用户不需要把同一份项目在多个工具间反复复制、改名和解释。资料、分析、方向、图像、决定和交付内容留在同一项目内，通过对象来源、版本和关联保持可回看。

### 3.2 从“结果图”变成“可解释的设计过程”

Morpho 不只保留最后一张图，还保留：

```text
原始资料来自哪里
哪些分析和结论被保留
设计定义为什么这样写
哪些方向被选中、备选或淘汰
主图从哪一轮发展而来
哪些局部被借用
哪些图已经用于交付
```

这些关系默认不铺满画布；用户只在需要时查看来源、版本、关联与决定依据。

### 3.3 从单轮 AI 回答变成连续 Agent

右侧只有一个连续 Agent。尚未压缩的聊天历史在有效 Token Budget 内完整参与后续回合；阶段、当前重点、方向、选择对象和 VisualBranch 只改变任务策略与资料选择，不创建独立聊天或历史孤岛。调研、设计定义、方向与视觉发展和交付准备仍使用不同判断重点，但由统一 Prompt Registry 和 Task Strategy Resolver 组合。

### 3.4 从短期上下文变成项目连续性

Morpho 通过结构化项目事实、七类当前有效项目记忆、六类当前有效阶段记录、原始聊天和版本化压缩摘要保持项目理解。接近模型有效上下文上限时，系统先维护稳定记录，再保存摘要版本与覆盖边界；后续携带摘要和边界后的完整消息，原始聊天继续持久化并可查询。用户不需要手工维护后台文档，也不需要每次换工作重点重新解释已经确认的方向、偏好和限制。

### 3.5 人做关键判断，AI 做理解、建议与执行

AI 可以分析、归纳、生成、整理和提出方案；但设计定义、主 / 备选 / 淘汰方向、主视觉锚点、项目级稳定偏好和重要交付结构必须来自用户的明确决定。

## 4. 总体原则

### 4.1 可以从空白开始，也可以从任何已有成果切入

Morpho 不把流程设计成“必须先做研究，再写定义，再出图”。用户可根据已有程度直接进入合适工作重点。

### 4.2 先看见方向，再决定方向

概念阶段的方向不能只靠文本标题和关键词比较。真正不同的方向要尽早获得可视预览；预览图用于判断潜力、结构、气质和可继续性，不等于最终主图。

### 4.3 主图优先是设计建议，不是视觉操作的通行证

当用户准备把一条路线收束为重点表达时，优先把核心产品形态、比例、关键部件关系和视觉语言做稳，再补更多表达图。这个顺序有助于保持方案一致性，但**不构成权限门槛**：从第一张预览图开始，用户就可以选中任意图继续发展、局部修改，或衍生角度、场景、CMF、细节和设计示意。

用户也可以把某张图设为**后续默认参考**（系统内部仍称主视觉锚点）。它只表示后续相关生成默认继承这张图的架构、比例、关键部件、CMF 与视觉语言；没有设定默认参考时，用户当前选中的图就是本次生成的主要参考。设定默认参考不会替换已有素材或交付引用。

### 4.4 画布以项目推进为主，不是节点工作流

画布从左到右帮助阅读项目推进，上下空间可容纳方向分叉和局部探索；但位置不决定对象类别、关系、状态或阶段归属。移动只是移动。

### 4.5 信息默认轻，详情按需出现

不在画布上堆满 Prompt、模型参数、关系线、版本号、任务状态和标签。对象的详细来源、版本、关联和决定依据放进底部详情栏按需查看。

### 4.6 不把正常设计过程做成任务管理

不做强制阶段打卡、百分比进度、任务队列、项目 KPI、必须分类的文件夹或操作流水账。阶段只是当前工作重点；Compare 是局部比较动作；用户可自然回头修改早期内容。

### 4.7 选中对象后给可编辑建议，不替用户执行

用户选中单个或多个对象后，系统可依据对象类型、数量和直接关系给出少量轻量建议，例如“读取并整理要求”“比较这些图”“继续发展这张图”。点击建议只将一句可编辑的自然语言填入右侧输入框；用户可修改、补充或直接忽略。建议不会自动发送、不会自动执行，也不会因选择本身改变用户当前正在推进的工作。

### 4.8 过程要可追溯、可迁移、可导出

项目应能导出最终成果，也应能保留人类可读的完整项目归档，并能通过可恢复备份继续编辑或迁移设备。三者的区别见《05_Morpho_项目入口、资产、搜索、导入与归档.md》。最终展板、PPT 等精细排版仍由 Figma 等专业工具完成；Morpho 当前负责把交付所需的内容、素材、结构和缺口准备完整。

### 4.9 图像生成先形成视觉计划，再编译 Provider Prompt

Agent 不临场自由拼接最终图片 Prompt。它先输出结构化视觉意图，区分要改变、必须保留、允许变化、图片角色、构图、视角、产品形态、CMF、场景、避免项、目标方向与用户明确参考；Morpho 再根据当前 Design Brief、方向修订、项目偏好、确定性参考解析、图片角色和目标模型适配器编译最终 Prompt。结构化意图、编译结果、参考解析和模型参数都保留来源。

`1 / 2 / 4 / 6` 只作为常用数量快捷项。用户明确要求 `3 / 5 / 9 / 12` 张或四个以上方向时可以执行；系统可透明分批，但不能把旧快捷项、总数 8 或方向最多 3 当作产品能力上限。

## 5. 总体工作流

### 5.1 六类可能出现的工作重点

```text
开始与输入
→ 探索（可选）
→ 调研
→ 设计定义
→ 方向与视觉发展
→ 交付准备
```

这是一组供 Agent 选择任务策略、供画布帮助阅读、供阶段记录归类的逻辑工作重点，不是六个必须完成的关卡，也不是聊天隔离边界。用户当前在推进什么，由他正在讨论、选择和要求 Agent 完成的任务决定；画布位置、方向、分支或单次选中对象不会切断早期未压缩聊天。

- 用户不清楚从哪里切入时，可先探索；
- 用户已有明确方向时，可跳过探索直接调研或直接进行视觉发展；
- 用户已有成熟方案时，可直接开始视觉发展或交付准备；
- 用户可在任何时候回头修改研究、设计定义或方向，而不需要“回滚整个项目”。

系统只会在出现确定性成果时准备下一步建议，例如研究与分析生成后准备“继续补资料 / 保留关键结论”。建议不立即打断用户；在用户下次准备继续聊天时轻量出现，用户可继续当前工作、采用建议或忽略。它不表示阶段完成，更不会自动切换工作重点。

### 5.2 开始与输入

用户把一句话、资料、草图、旧项目内容或已有设计带进来。系统帮助用户建立最小起点理解，但不急着把资料自动分类成永久标签，也不强迫先写完整 Brief。

### 5.3 探索（可选）

当用户只有模糊主题、活动题目或兴趣方向时，先讨论可能切入点。探索不是产品名称生成器；它要帮助用户找到值得研究、能产生设计差异的切口。真正保留的探索方向才进入画布和后续调研。

### 5.4 调研

用户围绕当前问题导入参考、材料、案例、竞品、旧资料或文档，AI 基于用户指定对象和当前语境形成研究与分析。调研的目标不是堆“调研报告”，而是找出会改变设计判断的发现、约束、机会和待验证问题。

### 5.5 设计定义

用户把真正成立的发现收束为一份当前有效的设计定义：核心问题、目标用户与场景、目标、原则、边界、避免项和已纳入的关键依据。设计定义是后续方向与视觉发展可默认参考的依据，不是项目开始时的强制表单。

### 5.6 方向与视觉发展

用户可以提出真正不同的概念方向，并尽早生成有差异的预览图。预览、主图、场景图、CMF 图、角度图、细节图和设计示意都是图像的**角色**，不是被阶段门槛分开的功能。

从任何一张选中的图开始，用户都可以继续发展、局部修改、比较、保留局部、衍生其他角度 / 场景 / CMF / 细节 / 示意，或直接用于交付。主图优先只是当用户希望收束某条路线时的推荐方式；设为后续默认参考是可选的一致性工具，不是生成其他图的前提。

### 5.7 Compare 比较

Compare 可以出现在调研、方向与视觉发展或交付准备中。它不独立占据一个固定阶段；比较产生的判断写回实际服务的阶段记录和必要的决策记录。

### 5.8 交付准备

交付区始终可用，但最终整理通常在后期成为工作重点。用户先明确要做什么：展板、PPT、作品集页面、素材包、报名材料、视频脚本或其他输出。系统优先复用项目内已有内容，先检查叙事和缺口，再决定是否需要补新图。

交付准备负责交付结构、逐页 / 逐模块文字、素材选择、图注、缺口与可选视觉参考图；它不承诺完成最终展板 / PPT 的精细排版、可编辑 PPTX 或 Figma 级编辑。

## 6. 核心概念与对象关系

| 概念 | 它是什么 | 在项目中的作用 |
|---|---|---|
| 原始资料 | 用户导入的图片、文件、链接、文字、草图、旧渲染等 | 保留原貌，作为分析、参考或生成输入 |
| 研究与分析 | AI 基于指定资料形成的候选分析 | 帮助理解材料，不自动成为项目事实 |
| 关键结论 | 用户明确保留的、会影响后续判断的发现 | 可进入设计定义、项目记忆或方向判断 |
| 设计定义 | 当前有效的设计依据 | 规定问题、用户、目标、原则与边界 |
| 概念方向 | 一条可独立判断的策略 / 产品逻辑 | 可处于待预览、主方向、备选或已淘汰 |
| 预览图 | 用于快速验证方向潜力的视觉结果 | 帮助判断策略、产品感与可继续性；也可直接继续发展或衍生其他表达图 |
| 主图 | 某一路线被重点收束的视觉结果 | 帮助稳定核心产品形态与表达基线，但不限制其他图像操作 |
| 后续默认参考（内部：主视觉锚点） | 用户明确设定为默认一致性基线的一张图 | 让后续相关生成默认继承其架构、比例、关键部件、CMF 与视觉语言；不是衍生素材的前提 |
| 衍生素材 | 围绕任意参考图生成的角度、场景、CMF、细节、示意或展示图 | 服务理解、探索、展示和交付；可以早于主图收束出现 |
| 交付模块 | 展板、PPT、作品集等交付中的可编辑结构 | 通过稳定引用使用项目内容，不吞掉源对象 |

完整对象操作见《02_Morpho_工作台、画布与对象规则.md》；状态、版本和项目记录见《04_Morpho_状态、版本、项目记录与记忆.md》。

## 7. 第一阶段范围与后续边界

### 7.1 第一阶段必须走通的核心链路

第一阶段至少要让用户能够：

```text
创建或继续一个项目
```
