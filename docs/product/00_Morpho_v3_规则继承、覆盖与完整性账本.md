# Morpho v3.1：规则继承、覆盖与完整性账本

> **用途**：这是 Morpho v3 文档组的迁移控制文件，不是另一份简略产品介绍。它用于防止已确认机制在“更新文档”时被无声明地删掉、缩写掉或改成别的规则。  
> **当前状态**：第一批迁移完成；作为后续 v3 正文的唯一继承依据。  
> **适用范围**：产品规则、交互规则、AI 连续性规则、项目记录规则、资产与归档逻辑。  
> **不锁定的内容**：数据库、文件系统、JSON Schema、模型调用架构、前后端实现与部署方案。

> **v3.1 原型前更新（2026-06-22）**：本轮将对象选择建议、确定性下一步建议、连续视觉发展、可选默认参考、交付准备边界、失败 / 重开体验正式写入正文并同步校验。

> **Milestone 3 工程补充（2026-06-25）**：AI Operation Runtime 是对 03 / 04 / 05 的工程实现补充，不覆盖既有产品规则。Operation 是受控、有限步骤的工作流，不是无限自主 Agent Loop；Proposal 必须经用户确认后才可成为正式领域对象。M3.2 中，chat / research 可使用真实选中图片输入和 MiMo 原生 web_search；联网由模型在工具可用时判断是否需要，imageGeneration 永不启用联网工具。Citation 只来自 provider 返回的真实来源快照。

## 1. 为什么需要这份账本

v1、v2 和《跨窗口交接与当前规则汇总》不是简单的“新文档完全替代旧文档”关系。

v1 首次把 Morpho 的连续性机制写完整：阶段 Context / Thread、自动压缩、阶段记录、长期项目记忆、Markdown / YAML / 结构化数据职责、逻辑文件名和阶段记录模板。v2 保留了这套产品方向，但在重写时把不少细节压缩成“阶段聊天、项目记忆、阶段总结”等概述。交接稿又重点修正了画布、右侧 AI、Compare、对象语义等交互规则，却没有逐项重述 v1 的连续性细节。

此前把 v1 标成“已废弃，不作为规则依据”，会造成错误理解：

```text
后面的文档没有重复写
→ 被误认为旧规则已失效
→ 已确定的机制被重新讨论、重新发明或直接删掉
```

v3 不再采用这种更新方式。以后只有两种情况可以让旧内容失效：

1. 后文**明确写出**了与它冲突的新规则；
2. 后文**明确缩小了产品边界**，使旧能力不再属于当前产品。

“没有再次写到”“章节变短”“示例没有列到”都**不能**视为删除。

## 2. v3 的文档优先级与使用方式

v3 完成后，后续讨论、原型、设计稿和开发计划只需要读取 v3 文档组；v1、v2 和交接稿只作为规则溯源材料。

### 2.1 当前规则优先级

```text
v3 中明确写出的当前规则
> 本账本中标为“本次迁移已确认补充”的规则
> 交接稿中已确认、且未被后续确认修改的规则
> v2 中未冲突的稳定总纲
> v1 中未被明确替换的完整细节与模板
> 调研报告与竞品材料（仅作依据，不自动转成功能）
```

### 2.2 以后更新 v3 的最低要求

任何更新都必须同时完成四件事：

1. 在受影响的正文中修改当前规则；
2. 回到本账本，记录“旧规则 → 新规则”的明确变化；
3. 检查同一规则是否在其他正文出现，避免只改一处；
4. 若只是为了精简表达，保留原有约束、模板、边界和例外，不得把它们无声明删除。

不允许再写：

```text
“新版本替代旧版本，旧文档不再作为依据”
```

除非新版本已经逐项吸收、替换或明确废弃旧内容。

### 2.3 状态标记

| 标记 | 含义 |
|---|---|
| **继承** | 旧文档已经确定，后文没有明确冲突；v3 必须保留。 |
| **替换** | 旧规则被后文明确改掉；v3 只保留新规则，并写清替换关系。 |
| **合并** | 多份文档从不同角度描述同一机制；v3 需合成一套不重复的当前规则。 |
| **补全** | 原有机制仍成立，但旧文档只留了概述或留下缺口；v3 需要恢复完整边界或模板。 |
| **待后续确定** | 原文明确说尚未定；不得把助手推测写成既定功能。 |
| **技术保留** | 产品层已确定逻辑职责，但物理存储、字段和实现方式留给技术方案。 |

01_Morpho_产品定义与总体流程.md
02_Morpho_工作台、画布与对象规则.md
03_Morpho_AI工作流程、阶段Context与连续性机制.md

05_Morpho_项目入口、资产、搜索、导入与归档.md

## 7. 必须恢复、不能再被“概述化”丢失的内容

以下是本次审计发现的高风险内容。v3 正文必须明确写出，不能只留一句“AI 有项目记忆”。

1. **完整 Context 合同**：阶段工作重点 / 提示词、当前项目记忆、相关阶段记录、当前阶段压缩摘要、选中对象、当前方向 / 锚点、用户最新输入的组合规则。
2. **阶段提示词机制**：不同阶段有不同职责；当前不锁死提示词文本，不等于取消该机制。
3. **自动压缩机制**：同阶段过长、阶段切换、关键决定、交付前整理时如何继续内部 Context；用户不手动压缩。
4. **阶段记录的 8 个栏目**：它们是每份记录的内容模板，不是“八类阶段记录”。
5. **7 份长期项目记忆的固定逻辑职责和名称**：不能用几个泛泛的 UI 分区取代。
6. **结构化状态与可读记录的更新边界**：锚点、方向状态、关系、版本等直接写；原因、偏好、影响等才归纳。
7. **Markdown / YAML / 结构化数据的职责分层**：保留逻辑分工，不把物理实现写死。
8. **锚点的可追溯信息**：锚点不仅是一张图，还关联视觉路线、来源、版本、参考、用户反馈、保留原因和稳定视觉倾向；这些信息应分别存于结构化关系与可读记录中，不堆成图片卡片。
9. **交付类型的完整范围**：展板、PPT、作品集只是常见入口，不应无声删掉素材包、报名材料、视频脚本和其他输出。
10. **归档与备份的差别**：完整项目归档服务阅读、复盘、交接；可恢复备份服务继续编辑和迁移；两者都不同于普通资料导入。
11. **过程可追溯性**：来源、版本、关联、决策和交付引用是底层关系，不意味着默认满画布画连线。
12. **用户不管理内部文档**：项目记忆和阶段记录为 AI 连续性与归档服务，不做第二套项目管理界面。

### 8.1 技术实现问题

- 运行时用数据库、文件、对象存储还是混合存储；

- JSON 字段、ID、索引、事件日志和版本快照如何设计；

- 可恢复备份的压缩包目录、加密、同步与冲突策略；
- 阶段 Thread 与模型会话在工程上如何管理；
- 自动摘要何时异步执行、怎样控制成本和失败恢复。

### 8.2 后续产品深化问题

- 阶段提示词的正式文本；
- 委托调研的合规数据源、可信度、版权、成本与用户确认流程；
- 高级模型路由、用户自带模型；
- 更复杂的多项目检索、协作、评论、权限；
- CAD / 3D / 工程数据接入；
- 成熟的自动排版与可编辑展板 / PPT 生成。

这些项在 v3 中只能写为“后续能力”或“技术方案待定”，不能因当前讨论方便而被写成产品已确定功能。

## 12. 给后续撰写者的硬性提醒

1. **先查账本，再写正文。** 每一条规则都先判断：继承、替换、合并、补全、待定还是技术保留。
2. **不因“文档更短”而删机制。** 简短可以通过引用和分文档完成，不能靠抽象掉条件与模板完成。
3. **不把系统内部概念变成用户工作负担。** 用户操作画布对象、状态与自然语言决定；系统维护 Thread、记忆、记录和索引。
4. **不把正常设计过程企业化。** 不做任务看板、进度 KPI、强制分类、操作流水账和不必要的确认弹窗。
5. **不把技术实现写成产品承诺。** 逻辑职责可以确定；存储目录、数据库、事件流和 Schema 等留给后续技术方案。
6. **不重新打开已确认的规则。** 除非发现与另一条当前规则真实冲突，或用户明确要求修改。
