## 1. 四类不同的项目信息，不能混为一谈

Morpho 的连续性不是靠一份“大项目总结”维持，而是由四种不同层次的信息共同构成：

| 层次 | 保存什么 | 更新方式 | 用户日常是否直接管理 |
|---|---|---|---|
| **结构化项目状态** | 当前工作重点、对象状态、关系、版本、锚点、交付引用、隐藏等 | 系统直接读写 | 否；用户通过真实对象和明确操作改变 |
| **当前有效项目记忆** | 跨阶段持续成立的项目事实、设计定义、稳定偏好、关键决定、开放问题、交付计划 | 只在确认信息变化或需要整理时更新 | 否；系统自动维护 |
| **阶段记录** | 某一阶段目前成立了什么、为什么成立、还有什么未解决 | 随相关内容更新 / 修订 | 否；系统自动维护 |
| **内部压缩摘要** | 当前阶段近期讨论、尝试和局部工作上下文 | 自动压缩时更新 | 否；不作为用户工作对象 |

这四类内容互相引用，但不互相替代。

例如，用户把锚点从图 A 换成图 B：

```text
结构化项目状态：当前锚点 A → B
版本 / 来源 / 下游关系：直接更新
阶段记录：只在需要表达“为什么换锚点、影响哪些后续素材”时更新受影响段落
项目记忆：只在该决定形成跨阶段稳定依据时更新相关决定
内部压缩摘要：仅在当前 Context 需要整理时更新
```

不应该让一次简单状态切换触发模型重读整个项目、重写全部文档或制造新的长篇总结。

## 2. 状态的总原则

状态只在三种情况下应该对用户可见：

```text
它会改变项目默认继续方向；
它需要用户注意或做决定；
它表达短暂但必要的进行 / 异常反馈。
```

除此之外尽量留在结构化状态和详情中。Morpho 不是任务管理工具，不用到处堆满“候选、已选、处理中、完成度、负责人、进度”等标签。

### 2.1 一条对象最多一个核心状态

一个对象通常只显示一个最重要的状态；必要时再加一个“待复核”。

不要形成：

```text
已生成 / 候选 / 已选 / 当前 / 有关联 / 已使用 / 已完成
```

这样的标签堆。

### 2.2 这些不是项目状态

以下属于交互或画布状态，不应混进项目演进状态：

```text
已选中
已多选
已锁定
已隐藏
已折叠
在当前视野外
```

- 锁定只锁布局，仍可查看、讨论、作为 AI 输入；
- 隐藏只临时移出画布，不删除、不淘汰、不改变默认设计方向；
- 删除就是删除；
- 已淘汰是保留的设计决策状态。

## 3. 各类对象的可见状态

### 3.1 研究与分析、关键结论

研究与分析是 AI 基于指定资料形成的候选分析，不是自动成立的项目事实。

关键结论一旦被用户明确保留，本身就代表它已成立；因此不显示“已确认”。可见状态只保留：

```text
待验证
已替代
```

- **待验证**：有价值但证据不足，不能当作当前稳定依据；
- **已替代**：曾经有效，但被更新结论或新证据替代；保留来源与历史价值。

### 3.2 设计定义

设计定义默认不显示“当前版本”标签。只要它被设为当前有效设计定义，系统已知它是默认依据。

只有出现实质性、尚未应用的修改时，显示：

```text
有修订草稿
```

实质修改包括核心问题、用户 / 场景、目标、原则、边界、避免项或已确认视觉倾向的变化。改标题、措辞、顺序或明显错误可直接编辑，不需要人为制造一版修订。

### 3.3 概念方向

方向的可见状态为：

```text
待预览
主方向
备选
已淘汰
待复核（必要时）
```

含义：

- **待预览**：方向已经提出，但尚未通过图像预览验证；
- **主方向**：AI 后续默认继续推进的方向；
- **备选**：保留，但不会被自动持续推进；
- **已淘汰**：不再作为默认路线，但对象和原因保留，仍可 Compare、借用局部或恢复；
- **待复核**：因锚点替换、定义更新等明确事件，可能需要用户重新判断。

不显示“探索中、候选、已选、已生成”等冗余状态。AI 可提出建议，但只有用户明确决定才能改变主方向、备选或淘汰。

### 3.4 图像与视觉素材

图像不显示长串内部生成状态。可见信息保持轻量：

```text
角色标签：预览 / 主图 / 场景 / CMF / 细节 / 设计示意等
后续默认参考（内部：主视觉锚点）
待复核（必要时）
```

起始图、完整 Prompt、模型参数、生成批次、版本细节、参考关系等放在底部详情栏的来源 / 版本 / 关联中按需查看。

### 3.5 交付模块

交付模块只显示真实缺口，例如：

```text
待补：安装逻辑示意
待补：使用场景
```

不显示百分比式进度，也不例行显示“已完成”。模块是否已经足够用于当前交付，由用户和 AI 在具体交付检查中判断，不伪装成精确 KPI。

## 4. 图像版本、视觉路线与分支

### 4.1 所有 AI 图像结果都是新对象

无论是整图继续、局部修改、换材质、换背景、调比例、改场景还是借用局部，AI 都创建新的图像对象。

```text
不覆盖来源图
不自动替换交付引用
不删除未采用图
```

同一轮返回的一组图片是并列结果，通常以合集出现；合集成员不是彼此的版本。

### 4.2 正常视觉发展与新视觉分支

正常视觉发展沿来源图右侧继续。无论来源图当前被称为预览、主图、场景或其他角色，材料、颜色、背景、视角、局部比例和局部部件调整通常仍属于同一路线的继续。

出现以下变化时，才创建新的视觉分支：

```text
产品架构改变
核心使用机制改变
整体产品类型改变
```

新分支在来源路线的上方或下方展开；原路线保留，不自动改变主方向、设计定义、锚点或交付内容。

### 4.3 从旧图继续

用户从较早版本继续，只是从该图开始一条新路线：

```text
旧图
→ 新一轮结果
→ 新路线
```

它不是“把项目回滚到过去”，不会自动：

- 改当前主方向；
- 改主视觉锚点；
- 改当前设计定义；
- 替换交付引用；
- 让后续素材失效。

Morpho 不建立全项目时间点回滚或独立“恢复旧版本”系统。用户要删对象就删除；要继续旧路线就从旧图继续。

### 4.4 图像批次与合集

一批生成结果是一个合集，合集默认初次展开并聚焦。用户可自行折叠、展开、拖出成员、删除成员或用其中某一张继续发展。

旧合集不会因为新一轮生成、锚点变化或方向变化而被系统自动折叠、弱化、淘汰或移动。

### 4.5 版本关系的查看

版本关系默认隐藏。用户在底部详情栏打开“版本”时，只查看直接关系：

```text
直接父版本
当前对象
直接子版本
```

关系线临时出现，不形成满画布版本网。

## 5. 设计定义修订、方向变体与交付变化

### 5.1 设计定义修订

- 草稿阶段：可直接反复编辑；
- 已应用为当前有效定义后：实质性改变先形成修订草稿；
- 用户点“应用这版修订”后：新内容成为当前有效定义，旧版本在版本历史中可回看；
- 应用新定义时：系统可轻提示当前主方向和相关内容可能需要再看，但不自动把所有下游对象标成待复核。

只有用户明确要求“按新定义检查已有内容”时，才针对相关内容进行复核标记或分析。

### 5.2 方向变体

方向名称、描述、关键词等文字可直接编辑。

若改变方向的核心策略、产品类型、使用逻辑或总体架构，不使用“方向 B v2”覆盖旧方向，而创建一个新的**方向变体**：

```text
新方向对象
→ 放在原方向附近
→ 默认待预览
→ 不自动继承主方向 / 备选 / 已淘汰状态
```

这样旧方向的来源、预览与决定理由仍可追溯。

### 5.3 交付模块的变化

交付模块可直接编辑：

```text
布局
裁切
标题
说明文字
替换图片
拆分 / 合并模块
```

想尝试一套完全不同的叙事或整体版式时，直接复制该交付模块，在旁边试，不创建“交付修订草稿”体系。

交付引用是稳定实例。上游有了新图、源图移动、源图删除或出现新版本时，已放入交付的引用不会静默替换。

## 6. 后续默认参考（内部：主视觉锚点）

### 6.1 它是什么，不是什么

后续默认参考是用户明确设定、将作为一段后续相关生成的默认一致性基础的一张图。系统内部沿用“主视觉锚点”名称，但用户界面可使用更自然的“设为后续默认参考”。

它不是最近继续过的图，不是任何一张候选自动升级后的名称，也不是生成角度、场景、CMF、细节或示意图的通行证。没有设定默认参考时，用户当前选中的图就是本次生成的主要参考。

设定后，相关生成默认继承其：

```text
产品架构
比例与体量
关键部件关系
CMF 基线
视觉语言
```

用户仍可从任何其他图继续发展或衍生表达。不同素材类型可在各自允许范围内改变视角、场景、局部放大、材料或表达方式，具体边界见 AI 工作流程文档。

### 6.2 锚点的可追溯信息

锚点不是孤立的一张图片。系统需要保留与它有关的可追溯信息，但不把所有信息堆在卡片上：

| 信息 | 主要保存位置 |
|---|---|
| 锚点图、直接父版本、直接子版本、参考图和来源关系 | 结构化关系与底部详情 |
| 生成参数、局部编辑标注、Prompt / 生成历史 | 结构化系统数据与详情 |
| 用户明确的保留原因、关键反馈、决定理由 | 决策记录与方向与视觉发展阶段记录 |
| 当前稳定视觉倾向、项目级避免项 | 设计定义 / 偏好与避免项 |
| 从锚点派生并已被交付引用的素材 | 关联与交付引用关系 |

### 6.3 设为后续默认参考

用户明确设定后，系统直接更新结构化状态，并在有意义的节点更新方向与视觉发展记录和决策记录。

不需要每次重新调用模型、重写全部项目记忆或让用户管理文档。

### 6.4 替换已有默认参考

首次设为后续默认参考可直接执行。替换已有默认参考时，给一张简短确认卡：

```text
用这张图替换当前后续默认参考。
之后相关生成将以它为默认基线；已有素材不会被删除或替换。
```

提供两个选择：

```text
只替换默认参考（默认）
替换默认参考，并标记相关素材待复核
```

第二种只标记旧锚点的**直接延展素材**，例如多角度、细节、使用场景、CMF、设计示意或展示主视觉：

- 成组素材：标记合集；
- 单张素材：标记单张图。

不要标记：

- 原始研究资料；
- 不相关方向预览；
- 旧视觉发展路线中的普通候选；
- 无关图片；
- 交付模块本身。

### 6.5 待复核后的操作

对待复核素材，用户可：

```text
保留
基于新的默认参考重新生成
查看它被用在哪里
```

系统不自动删除、替换、重排或重新生成。

## 7. 项目记忆：固定 7 份长期逻辑文档

项目记忆记录的是**当前仍有效、跨阶段需要持续使用的确认信息**。它不是聊天摘抄，不收录每一张图、每个普通候选、临时分析或随口想法。

逻辑上固定保留以下七份：

| 逻辑文件名 | 中文职责 | 记录什么 | 不记录什么 |
|---|---|---|---|
| `project_overview.md` | 项目概览 | 项目名称、课题 / Brief、目标、范围、明确交付要求、少量已确认基础事实与限制 | 当前阶段、聊天摘要、所有调研全文 |
| `design_brief.md` | 设计定义 | 当前有效核心问题、用户与场景、目标、原则、边界、避免项、已纳入的关键依据 | 旧版全文、未应用草稿、每次微调 |
| `user_preferences.md` | 偏好与避免项 | 用户明确确认的项目级视觉、形态、表达偏好和明确避免项 | 只影响一轮图像的临时要求、AI 猜测 |
| `decision_log.md` | 决策记录 | 关键选择、理由、关联对象、发生时间 | 普通拖动、裁切、常规生成、微小文案修改 |
| `rejected_directions.md` | 已淘汰方向 | 当前处于淘汰状态的方向、淘汰原因、仍可借用局部 | 单张不喜欢的图、普通未选候选 |
| `open_questions.md` | 待确认问题 | 会影响后续判断的开放问题、影响范围、关联对象 | 随口问题、低影响小疑问、任务清单 |
| `output_plan.md` | 交付计划 | 已确认交付物、叙事结构、已选内容、明确缺口 | 元素坐标、裁切历史、排版过程流水账 |

### 7.1 七份记忆之间的分工

- **项目概览**回答“这是什么项目”；
- **设计定义**回答“当前依据什么做”；
- **偏好与避免项**回答“这个项目整体喜欢 / 不要什么”；
- **决策记录**回答“为什么这么选”；
- **已淘汰方向**回答“当前不继续什么、但还有什么局部价值”；
- **待确认问题**回答“什么尚未成立、会影响下一步”；
- **交付计划**回答“要怎样讲清项目、还缺什么”。

同一信息不能为了“看起来完整”复制到七份文档。需要时以对象链接或简短引用关联。

### 7.2 写入边界

默认可写入当前有效项目记忆：

```text
用户确认关键结论
用户应用设计定义
用户设为主方向 / 备选 / 已淘汰
用户锁定或替换锚点
用户确认交付结构
用户明确确认项目级稳定偏好或限制
```

默认不写入：

```text
用户随口想法
AI 方向候选
普通图像生成与普通变体
临时分析
只属于当前路线的一次局部偏好
未确认推断
```

AI 认为某项可能是项目级偏好，但用户没有明确确认时，应以自然语言询问是否作为项目长期依据，或只按当前轮次处理；不能自行升级。

### 7.3 用户不日常管理这些文档

用户日常操作的是：

```text
画布对象
方向状态
设计定义
主视觉锚点
交付内容
右侧聊天中的明确决定
```

系统据此维护项目记忆、阶段记录、关系、版本和引用。项目记忆与阶段记录不应被做成一套需要用户日常打开、编辑、删除和维护的“文档管理工作台”。

它们的主要用途是：

```text
AI 跨阶段持续理解项目
完整项目归档、复盘与交接
```

这不排除在归档、按需回看或问题追溯时提供人类可读材料；但产品不要求用户通过手改内部文档来改变项目事实。要改主方向、设计定义或锚点，应改真实对象和明确状态。

## 8. 阶段记录：保留 8 栏模板，但作为可修订的当前有效记录

阶段记录承担 Handoff 功能：让系统和未来阶段理解“这个阶段目前成立了什么、为什么成立、还有什么没定、下一步应该注意什么”。

它不是不可变的历史快照。用户后面推翻调研结论、修订设计定义、改变方向或替换锚点时，相关阶段记录可以更新 / 修订；旧版本按需作为历史保留。

### 8.1 记录类型与逻辑名称

以下是逻辑记录类型，不要求每个项目都有全部文件，也不锁定实际存储方式：

```text
stage_01_start.md
stage_02_explore.md
stage_03_research.md
stage_04_design_definition.md
stage_05_direction_visual_development.md
stage_06_delivery_preparation.md
```

Compare 不单独建阶段记录；它的结论写回实际服务的记录。预览、主图、场景、CMF、角度、细节和示意等内容，按同一条视觉路线记录在“方向与视觉发展”中，而不被拆成用户必须逐项通过的阶段文件。

### 8.2 每份阶段记录的 8 个栏目

每份阶段记录沿用 v1 已确定的内容骨架：

```text
1. 阶段目标与当前状态
2. 本阶段产出成果
3. 关键设计决策与原因
4. 被否定方向与原因
5. 用户偏好与反感点
6. 项目约束与稳定设定
7. 未解决问题与风险
8. 下一步重点
```

“下一阶段接力指令”改为“下一步重点”，以适应项目可以非线性回看、回改和跳转的实际工作方式。

某个栏目没有有效内容时，不应为了模板完整而填空话；在阅读材料中可隐藏空栏目。

### 8.3 各阶段重点记录什么

| 阶段 | 重点记录 |
|---|---|
| 开始与输入 | 项目起点、原始 Brief、用户带入资料、已确认基础信息、尚未澄清的前提 |
| 探索 | 被保留的切入方向、未继续的探索、下一步最值得验证的问题 |
| 调研 | 当前有效发现、现实约束、待验证问题、关键来源与证据边界 |
| 设计定义 | 当前设计定义如何形成、采用了哪些结论、哪些冲突或问题仍未解决 |
| 方向与视觉发展 | 方向状态、预览验证出的差异、视觉路线、保留 / 调整 / 避免内容、可借用局部、后续默认参考形成或替换的原因、重要衍生素材解决什么表达问题 |
| 交付准备 | 交付目标、叙事结构、已选内容、明确缺口与当前交付判断 |

### 8.4 更新规则

阶段记录不是每一次点击都重写。分两层更新：

#### 直接更新，不调用模型

以下是确定性变化，系统直接更新结构化状态、关系、引用和记录中的对象链接 / 时间等元信息：

```text
主方向从 A 改为 B
锚点从图 A 改为图 B
方向改为备选 / 已淘汰
对象被纳入设计定义
交付引用增加、删除或替换
版本、来源、关联、待复核状态变化
```

#### 需要语义整理，才调用模型

以下内容需要理解、归纳或表达意义：

```text
为什么改主方向
为什么淘汰某方向
设计定义修订改变了什么
用户形成了哪些项目级稳定偏好
某条调研结论为何被推翻
本阶段结果会怎样影响后续工作
```

模型只更新受影响段落，不例行重写整份阶段记录。

典型触发节点：

```text
用户做出带理由的关键决定
用户明确要求整理 / 总结
准备切换工作重点
同阶段 Context 需要压缩
准备导出完整项目归档
```

### 8.5 阶段记录与项目记忆的区别

| 问题 | 阶段记录 | 项目记忆 |
|---|---|---|
| 记录范围 | 某一阶段当前有效结果与过程判断 | 跨阶段持续成立的信息 |
| 是否保留阶段语境 | 是 | 只保留稳定结论，不保留完整过程 |
| 是否可因后续修改更新 | 是 | 是，仅更新仍有效内容 |
| 是否记录普通聊天 | 否 | 否 |
| 是否需要用户日常管理 | 否 | 否 |

## 9. 可读记录、元数据与结构化数据的职责分层

Morpho 保留三层职责分工，但不在产品文档里锁死运行时文件夹、数据库或 JSON Schema。

| 层 | 作用 | 典型内容 |
|---|---|---|
| Markdown | 给人和 AI 读的正文 | 项目记忆、阶段记录、设计决定、交付计划 |
| YAML 或等价元数据层 | 记录可检索的文档元信息 | 阶段、状态、关联对象、更新时间、版本指向 |
| 结构化系统数据 | 给系统直接读取与计算 | 画布位置、对象关系、版本链、Prompt、生成历史、Thread 状态、引用关系 |

逻辑模板示例：

```markdown
---
stage: direction_visual_development
stage_name: 方向与视觉发展
record_status: current_effective
updated_at: 2026-06-22
related_objects:
  - direction_b
  - preview_set_03
---

# 方向与视觉发展记录

## 1. 阶段目标与当前状态
...
```

这个例子用于固定信息职责和归档可读性；它不等于产品已决定必须把文件直接保存在用户本地某个目录，也不锁定字段名、存储方式或数据库结构。

### 9.1 Operation Log 不是项目记忆

Operation Log、聊天记录、ResearchObject、阶段记录和长期项目记忆不是同一种东西。

```text
普通聊天
→ 只保存聊天

Operation 执行
→ 保存 Operation 状态、输入快照、步骤摘要、工具结果摘要和 citation snapshot

用户保存 ResearchAnalysisProposal
→ 创建 ResearchObject
→ 创建来源关系
→ 更新调研阶段记录引用
```

保存 ResearchAnalysisProposal 不会自动生成或改写长期项目记忆、设计定义、方向状态或关键结论。只有用户明确将某条结论保留为长期依据时，后续才可通过独立确认路径创建 InsightObject 或更新稳定项目记忆。

Operation / Proposal 数据保持轻量。原始网页正文、大型文件提取内容、页面预览和原始 provider/tool 结果不进入 localStorage；需要长期保存的大型 artifact 应通过 IndexedDB 或未来等价本地 artifact 存储引用。

## 10. 关系、引用与可追溯性

过程可追溯是 Morpho 的核心价值，但不应让用户面对满画布关系网。

需要可追溯的关系包括：

```text
来源
版本
关联
局部借用
锚点派生
交付引用
关键决定依据
```

默认隐藏；用户在对象底部详情中按需查看一层直接关系：

- **来源**：直接上游资料、起始图、来源文档或用户说明；
- **版本**：直接父版本、当前对象、直接子版本；
- **关联**：直接被哪里使用，例如设计定义、方向、锚点、交付模块或阶段记录。

这保证用户能回看“为什么有这张图、从哪来、被哪里用了”，但不把整个项目变成节点图。

## 11. 本文件不锁定的事项

以下属于后续技术方案或更深层的产品深化：

- 阶段记录和项目记忆在运行时如何存储、增量更新、合并冲突和保留历史；
- YAML 是否以真实文件头存在，还是由数据库元数据等价实现；
- 结构化数据的具体字段、ID、索引、事件日志和版本快照；
- 项目归档、可恢复备份的精确目录、压缩格式、加密、同步与迁移策略；
- 是否提供只读项目记录浏览、以何种最轻量方式呈现；
- 高级批量复核、跨项目版本比较和协作审阅。

这些不影响当前已确定的产品原则：用户改变真实对象和明确状态；系统快速、直接地维护结构化状态；只有需要理解“为什么”和“意味着什么”时才整理可读记录。
